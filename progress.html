Chromebook auto-tiering

biggest gap A legible school Chromebook still has its whole session decided by four seconds of classroom Wi-Fi. Measured on the shipped module: a UHD 600 / Iris Xe Chromebook (heuristic caps it at medium, so corroborated=true, provisional=false) that sees a 4.8 s boot storm takes a single 3-rung leap medium->potato at 4.1 s - shadows OFF, 1 post pass - and 3.3 minutes of flawless 16.6 ms afterwards restores nothing, because recoveryState() returns 'corroborated by hardware evidence' and downSteps>0 blocks the up path. changesLeft 2, recoveriesLeft 0, session over. The storm-length cliff is one second wide: <=3.6 s storm = no change at all, >=4.8 s = potato for ever. The RTX 4070 (which needs no help) and the masked browser both recover on the identical stream; only the target hardware does not. The logic error is nameable: the heuristic's cap AT medium is a positive prediction that medium is affordable, so a 120 ms median measured at medium CONTRADICTS the heuristic - it does not corroborate it. 'Corroborated' currently means 'the GPU was named', not 'the measurement matches the prediction'. D3 asserts chromebook.settled.tier === 'potato' as a PASS, so the builder's own suite enshrines the failure.

Boot storm no longer decides the session: the first descent is provisional (1 rung, tail-gated, revocable once on measured inconsistency), corroborated hardware still leaps. 46/46 claims pass (A18-A23, D3 new); C ran 9/9 on real frames.
